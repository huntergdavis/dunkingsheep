# Inbox views and the new-write cutover

Tasks t5011 (reader/UI) and t5010 (writer/threads) ship in **one coordinated daemon, desk and Telegram bridge release**. Do not deploy the reader alone with empty new views. The UI offers only **Your inbox**, **VP**, and **Historical / prior versions**; there is no audience toggle.

The read-only 2026-11-14 metadata snapshot explains the former toggle failure: the current `codex-rust-owner` mailbox had 3,291 pane-sender rows without an audience tag versus 428 tagged `agent`. The root `owner` mailbox also mixed recorded web/Telegram human ingress and replies with null-transport agent rows. Absence of `audience=agent` is not evidence of a human message. The evidence is metadata only; message text is not a classifier.

## Additive contract

`message_threads` stores `message_id`, `thread_version=1`, nullable `parent_id`, `root_id`, `conversation_kind` (`human`, `vp`, `other`), and authenticated `sender_kind` (`human`, `agent`, `system`). The old `messages` table and its rows are unchanged. New root IDs reference the allocated message itself. The writer validates an explicit parent, copies its root and routing scope, and commits the message and metadata atomically. Clients cannot choose root IDs or trusted origin kinds. Human participation in a new VP thread promotes its versioned records to the human scope atomically; legacy records are never backfilled.

The writer slice must stamp web, Telegram and inbox-send origins from authenticated operations and canonical routing. A pane with the compatibility role `owner` can be the VP agent; role or display name alone does not establish human origin. Telegram external reply references must resolve to stored internal IDs; never infer lineage from text or timing. Legacy `reply_to` is not presented as newly verified lineage.

## Read contract

The existing paged `owner_conversation` API accepts `source_filter=human_threads|vp_threads|historical`. Old selectors remain compatible. New selectors require `include_internal=false` (or omission); this is compatibility metadata, not a UI control. All retain the existing privileged owner/service authorization. Human and VP participant views include their daemon-recorded thread rows across physical delivery mailboxes, so a human quick message delivered to a lane remains visible with its replies. They do not include unrelated `other` conversations. Historical and legacy selectors retain the prior owner-mailbox/lane envelope.

Human and VP reads require versioned sidecar metadata. Owner decision B: an agent message whose recorded recipient route is `human` appears individually in Your inbox even while its `conversation_kind` remains `vp`, with a link to that VP conversation. Earlier VP messages remain in VP. Agent delivery never promotes a whole thread; only an authenticated human message does. System messages and alerts do not qualify for this addressed-agent exception. Explicit Agent-only sends to the human root mailbox remain refused by the existing audience guard; Agent-only coordination targets the VP lane. Tagged replies inside an already-human thread remain with that human thread. VP shows visible System, Alert and Agent-only labels from recorded origin, reserved page metadata and audience; bodies never classify a message. Historical reads are the complement of the supported v1 human/VP predicates within the existing scope: prior rows, `other`, unknown kinds and future versions remain visible. A read-only `historical_reason` identifies the fallback; recorded lineage is preserved separately and no thread links are invented. Agent-only rows, reserved scheduled-dunk digests and the existing routine-mail markers receive visible labels rather than being hidden. Filtering precedes LIMIT and cursor resolution. A cursor from another view is refused. Browsing never marks, acknowledges, or changes a message.

The web projection and UI require confirmed view scope and explicit lineage fields. Historical link fields are present and null with a confirmed fallback reason and visible metadata labels; new fields include a canonical root, optional canonical parent, version and origin kind. Missing or mismatched metadata fails closed instead of displaying an unscoped response. New-message display roles follow recorded `sender_kind`; historical content and prior reply references remain unchanged and honestly labelled.

## Schema and rollback audit

The six-column `message_threads` contract remains unchanged. `message_thread_routes` separately stores canonical sender/recipient reply addresses (`human`, `vp`, stable lane mailbox, or unavailable), without trusting reusable pane IDs. `message_thread_refs` stores authenticated transport/channel/message coordinates, explicit external parent references and an unavailable-parent marker. DDL adds three tables, three indexes and three delete triggers, with no ALTER or backfill of legacy messages. The triggers remove associated metadata when an old writer deletes a message. Missing retained ancestors remain explicit IDs; they are not silently reattached. Unit coverage opens the archived DB fixture, proves every prior schema definition unchanged, exercises old SELECT/DELETE SQL, and checks idempotent reopening.

Before release, capture the actual schema delta and run the pinned old daemon/desk binaries against a **private fixture** with the sidecar present. Rollback must drop `message_threads_delete`, `message_thread_routes_delete` and `message_thread_refs_delete` before restoring the old binary while leaving additive tables intact; rehearse that exact sequence. Record the old-binary compatibility receipt, independent artifact review, activation authorization and rollback pins. The SQL/schema unit check alone is not a claim that the old binary has been exercised. Preserve historical browsing and attachment access; t5014 will add the reviewed mailbox archive lifecycle without changing these lineage rules.

## New producers and explicit replies

Only the web route authenticated as an actual owner session selects private `owner_ingest_thread` / `inbox_send_human`. Agent API sessions retain the unversioned legacy ingress; a VP agent role cannot claim a human sender. The paired private-chat Telegram bridge uses the private ingress operation with actual chat and message IDs. Its pane-less system token must have the exact registered label `telegram-bridge`; watchdog, timers and other system labels are refused for both human ingress and thread delivery receipts. Web ingress requires the web transport, bridge ingress and receipts require Telegram. The service unit uses the dedicated 0600 `~/.config/dunkingsheep/telegram-bridge-token` file. Release requires VP provisioning this token and pinning the bridge unit before switching; never reuse the shared system or desk token. A missing or prior-version Telegram parent starts an explicit new root with an unavailable-parent notice. There is no body, subject, timestamp or pane-ID matching.

Normal daemon inbox sends stamp origin, routing scope and canonical reply addresses after PM routing. CLI/MCP callers may supply an explicit `parent_id` (`inbox send <recipient> --reply-to i42 <body>`). Normal lanes must be authorized to read that parent in their own mailbox. Clients never supply a trusted root or origin. Legacy `inbox_send` and `inbox_read` response shapes remain unchanged even for versioned messages; only private human-send receipts and explicit thread-aware views expose lineage. Human web replies use `/api/owner-send` with the exact parent ID; the daemon derives the peer atomically from stored routes. Versioned `owner reply` can answer a reply; the old one-answer rule remains for prior-version questions.

Human ingress keeps legacy `reply_to` null, so an old Telegram bridge cannot echo incoming replies as outbound answers after rollback. Agent answers preserve the originating transport and legacy outbox edge. Successful Telegram sends record every chunk's external message ID in the same transaction as the delivery receipt; a conflicting mapping rolls back the complete receipt. Ingress retries deduplicate inside the same writer transaction as message allocation and lineage insertion.

Human participation promotes all versioned records sharing a root into Your inbox and advances `view_revision` atomically. The UI drops cached rows and cursors when that revision changes; it does not keep promoted human conversations in the VP cache. It renders only stored parent/root links and marks retained ancestors outside the loaded window honestly. Failed or mismatched reply receipts keep the draft, with one request in flight. Historical messages offer a new conversation through Compose; no reply controls or invented lineage are added.
