# Worker identity migration (t4553, proposal only)

The current owner and worker processes run as the same Unix user. That user can read the owner credential and has unrestricted noninteractive sudo. File permissions, token-path concealment, a pane label, and process ancestry cannot isolate an adversarial worker under that arrangement. The partial owner-token pane-ancestry gate in this worktree only rejects direct calls from non-owner panes; a detached/reparented worker and same-UID privilege remain outside its guarantee. It must not be described as completion of t4553.

## Intended boundary

Run new worker and reviewer agents as dedicated Unix principals distinct from the owner/daemon principal, with no sudo, no supplementary privileged groups, no access to owner home/configuration or service tokens, and a private home. Prefer a distinct UID per lane: a shared worker UID permits workers to read or modify each other's state and potentially impersonate each other. If sharing is proposed, explicitly define that mutual trust and prove lane binding cannot be forged. Provision only required authentication and tool configuration. Grant project worktree access narrowly to the intended worker principal or project group; validate that it cannot change owner configuration, daemon binaries, socket policy, credential files, or other projects. Shared writable worktrees, build caches, hooks, and scripts are authority channels: an owner process must not execute worker-writable code with owner privileges without a separately defined and reviewed trust boundary. Determine each worker's needed network, git, and build-cache access before migration; do not copy owner credentials.

Provide a dedicated worker-facing Unix socket in a directory traversable by the worker principal, with ownership and mode set explicitly. Retain the existing owner socket and owner credential path for the detached owner app server. The daemon must obtain PID **and UID** from kernel `SO_PEERCRED` on every connection and independently constrain worker-UID requests to their live, PID/start-bound registered lane and scoped role. An owner-role service token presented by a worker UID must be refused even if the token is known and the request omits or forges a pane claim. Do not trust a request-supplied UID, PID, role, path, or token label as proof. Prevent worker UIDs from modifying the daemon's role/token stores or creating or changing trusted UID mappings. Review how tmux pane ancestry, `/proc` visibility and PID namespaces behave for cross-UID workers before using them for authorization; an unreadable, stale, or ambiguous binding fails closed.

A forwarding proxy that reconnects as the daemon user discards the original kernel peer UID unless it supplies an independently authenticated, unforgeable identity. It must not be treated as a transparent peer-credential boundary. Current server binds one mode-0600 socket and reads only the peer PID, so a reviewed implementation is required before a different UID can use the daemon. A second listener or direct alias must preserve the kernel peer UID; verify behavior rather than assuming it. Configure the worker socket so it does not inadvertently open the owner socket or credential directory.

## Staged verification and cutover

1. Inventory actual owner and worker dependencies and identify the detached owner app-server process using metadata only. Confirm all owner-role token uses and live service needs; logs do not currently correlate every request to token identity. Prepare a dedicated principal and test data in an isolated environment, with no production token copies.
2. Build and independently review the daemon peer-UID, socket and lane-binding implementation and the worker launch configuration. Exercise an isolated real daemon with a distinct worker UID: legitimate worker operations succeed; the same worker with a known scratch owner token is denied with correct, missing and forged pane claims; stale/reused process identity and unavailable lookups fail closed; a legitimate detached owner and an owner pane continue to succeed. Verify private home, sudo denial, project scope and lack of owner-token access. Capture outcomes without printing tokens or private messages.
3. Stage the new daemon and socket in parallel with current services where supported. Verify exact artifacts, service configuration, ownership, socket permissions and rollback before activation. Obtain a coordinated quiet window for any daemon switch. Test the real detached owner path and a disposable worker on the new principal before migrating production workers.
4. Move one willing, idle worker to the new principal in a new lane; verify its tools, project access, daemon role, message delivery and task operations. Migrate remaining workers at their checkpoints without interrupting active work. Keep old workers explicitly recorded as **not isolated** until replaced.
5. Remove or supersede globally readable owner-credential directions as soon as the owner authorizes it; this reduces accidental exposure but is not containment. Only after every relevant worker is migrated and independent verification passes, retire the shared owner-token route and rotate the exposed credential using an owner-controlled process; rotation while same-UID workers can reacquire it does not establish isolation. Confirm the new owner path works first. Maintain a tested rollback that restores owner access without giving worker principals owner privilege; never roll back by distributing an owner token to workers.

The global owner-identity context entry still contains credential-use guidance. Its retirement or supersession is owner-gated and was requested through the coordinator; until independently verified, do not claim that exposure is removed. The reported worker acknowledged the stop instruction, but the current token remains usable by other same-UID processes. The observed timed-out inbox read cannot be correlated to the nearby metrics events because those events do not record token identity.
